## 2. 数智财税基础章节【工作台key:chapter_tax】
> 面向PM：懂业务规则、系统流程、风险点，不做会计做账。

### 今日知识点：增值税发票的电子化与OCR识别

1. 核心概念：
   - 增值税发票是企业发生购销业务时开具的法定凭证，分为增值税专用发票和增值税普通发票。
   - 电子发票是以电子文件形式存在的发票，具有与纸质发票同等的法律效力。
   - OCR（光学字符识别）是指通过图像识别技术，自动读取发票上的文字信息，如发票代码、发票号码、金额、税率、购买方和销售方信息。
   - 数智财税产品通常将OCR识别与发票查验、入账、抵扣、归档等环节串联，形成自动化处理流程。

2. 业务场景举例：
   - 企业员工出差后，通过报销系统上传电子发票或拍照上传纸质发票，系统自动识别发票内容并填充报销单。
   - 财务共享中心每天需要处理大量进项发票，OCR识别后自动匹配采购订单和入库单，减少人工录入。
   - 税务风控平台通过识别销项发票信息，校验开票内容是否与实际业务一致，防范虚开发票风险。

3. 【必会】PM必须掌握：
   - 电子发票与纸质发票在法律效力、存储方式、查验方式上的区别。
   - OCR识别在发票场景中的典型输入（图片、PDF）和输出字段（发票代码、号码、金额、税额、开票日期等）。
   - 发票识别后的业务流向：识别 -> 查验真伪 -> 入账 -> 抵扣/归档。
   - OCR识别存在识别错误率，产品设计中必须提供人工复核入口。
   - 涉及敏感财务数据，需要考虑数据安全和权限控制。

4. 【不必深入】PM不需要深入：
   - OCR的具体算法原理（如CNN、Transformer在图像识别中的应用）。
   - 增值税的复杂计税规则和企业会计准则的具体分录。
   - 发票版式文件的底层解析技术（如PDF结构、OFD格式）。
   - 税务系统的接口报文加密细节。

5. 业务风险 & 产品设计注意点：
   - 识别准确率风险：手写发票、模糊照片、印章遮挡都会导致识别失败或错误，产品应设计置信度提示和人工修正流程。
   - 合规性风险：电子发票的原件归档要求、重复报销校验、真伪查验是监管重点，产品需内置查重和验真能力。
   - 数据隐私风险：发票包含企业交易信息和个人信息，需严格控制访问权限和传输加密。
   - 用户体验提示：上传发票后应明确告知用户识别结果状态，避免让用户误以为系统100%准确。

## 3. AI产品基础章节【工作台key:chapter_ai】
> 面向PM：懂能力边界、适用场景、局限性，不用钻研算法原理。

### 今日知识点：大语言模型的能力边界与PM视角

1. 基础概念通俗解释：
   - 大语言模型（LLM）是一种通过海量文本训练出来的AI模型，核心能力是根据输入文本预测最可能的下一个词，从而生成连贯的回答。
   - 它擅长：文本生成、信息抽取、语义理解、格式转换、简单推理和代码辅助。
   - 它不擅长：精确计算、实时信息获取、 long-chain 复杂多步骤任务、保证事实100%正确。
   - 幻觉（Hallucination）是指模型会自信地生成看似合理但实际错误的内容，这是PM设计AI产品时必须重点考虑的问题。

2. 现实产品落地案例：
   - 智能客服：用大模型理解用户问题，从知识库中检索答案并生成回复，但仍需人工兜底处理复杂投诉。
   - 合同审核助手：自动提取合同中的关键条款（如付款方式、违约责任），提示法务人员重点关注，但不直接替代律师判断。
   - 财报摘要生成：输入企业财报PDF，自动生成经营亮点和风险提示，供分析师快速浏览，但不用于投资决策。

3. 【必会】PM必须掌握：
   - Prompt工程基础：清晰表达任务、给出示例、限定输出格式，能显著提升模型效果。
   - RAG（检索增强生成）的基本逻辑：先检索企业私有知识，再让模型基于检索结果生成答案，降低幻觉风险。
   - 模型效果评估指标：准确率、召回率、用户满意度、幻觉率、响应时长。
   - 人机协同设计原则：高风险场景必须保留人工审核，模型输出不能作为最终决策依据。
   - 成本意识：模型调用按token计费，长文本和高频调用会显著增加成本。

4. 【不必深入】PM不需要深入：
   - Transformer架构、注意力机制、损失函数等底层算法细节。
   - 模型训练、微调、蒸馏的具体实现。
   - GPU集群配置、分布式训练框架等工程部署细节。
   - 复杂的数学推导和论文公式。

5. 产品需求设计、需求评审注意事项：
   - 明确场景边界：不要期望一个大模型解决所有问题，优先选择规则明确、容错率适中的场景。
   - 输出可控性：设计输出模板、限制生成长度、提供引用来源，让用户能验证答案。
   - 错误处理机制：当模型无法回答或置信度低时，产品应给出友好提示并转人工。
   - 数据安全：涉及企业财税、合同等敏感数据时，避免直接调用外部公有API，优先考虑私有化部署或RAG方案。
   - 评审时多问一句：「这个需求如果模型回答错了，用户会有什么损失？我们有没有兜底方案？」

## 4. 数据库基础章节【工作台key:chapter_db】
> 面向PM：懂数据存储逻辑、表、字段关系，不需要会搭建数据库。

### 今日知识点：关系型数据库基础概念（表、字段、主键）

1. 基础概念通俗解释：
   - 数据库是用来有组织地存储和管理数据的系统，关系型数据库是最常见的一类，数据以「表」的形式存储。
   - 表（Table）：类似Excel工作表，每一行是一条记录，每一列是一个字段。
   - 字段（Column/Field）：定义了数据的属性，例如「客户表」中的客户ID、客户名称、联系电话、注册时间。
   - 主键（Primary Key）：能唯一标识一条记录的字段，例如每个客户有一个唯一的客户ID，不能重复也不能为空。
   - 外键（Foreign Key）：用于建立表与表之间关系的字段，例如「订单表」中的客户ID可以关联到「客户表」。

2. 业务类比举例：
   - 把数据库想象成一家公司的人事档案柜：
     - 每个抽屉是一个「表」，例如员工表、部门表、工资表。
     - 每张档案卡片是一条「记录」。
     - 卡片上的每个项目（姓名、工号、部门）是一个「字段」。
     - 工号就是「主键」，每个人的工号唯一，不会混淆。
   - 在电商系统中：
     - 用户表存储用户基本信息，订单表存储交易信息。
     - 订单表通过用户ID关联用户表，这样就能知道「这个订单是谁下的」。

3. 【必会】PM必须掌握：
   - 能看懂ER图（实体关系图）中表与表之间的一对一、一对多、多对多关系。
   - 理解主键的作用：唯一标识、去重、关联其他表。
   - 知道常见字段类型：整数、字符串、日期、金额（小数）、布尔值。
   - 能根据业务需求判断需要哪些表和字段，例如在发票场景中需要发票表、发票明细表、报销单表。
   - 理解索引的基本作用：加快查询速度，但会占用存储并影响写入性能。

4. 【不必深入】PM不需要深入：
   - 数据库的安装、配置、性能调优。
   - SQL语句的复杂优化和索引底层实现（B+树等）。
   - 分库分表、读写分离、事务隔离级别等高级主题。
   - 存储过程、触发器、视图等DBA级别的技能。

5. 做需求、写PRD时相关注意点：
   - 字段命名规范：建议统一使用英文小写+下划线，例如 invoice_amount、create_time。
   - 必填字段与默认值：明确哪些字段必须填写，哪些可以有默认值，例如创建时间默认当前时间。
   - 数据字典：在PRD中附数据字典，列出每个字段的含义、类型、是否必填、示例值。
   - 关联关系：如果需求涉及多张表的数据联动，要在PRD中说明关联逻辑。
   - 扩展性考虑：字段设计要预留未来可能的扩展，但避免过度设计导致表结构臃肿。

## 5. SQL PM必备基础章节【工作台key:chapter_sql】
> 面向PM：看得懂简单SQL逻辑、理解取数逻辑，不要求手写复杂生产SQL。

### 今日知识点：SELECT基础查询与WHERE过滤

1. 概念/语法通俗讲解：
   - SELECT是SQL中最常用的查询语句，用来从数据库表中获取数据。
   - WHERE用于筛选满足条件的记录，相当于Excel中的筛选功能。
   - ORDER BY用于对结果排序，LIMIT用于限制返回条数。
   - 基本结构：`SELECT 字段 FROM 表名 WHERE 条件 ORDER BY 字段 LIMIT 条数;`

2. 业务场景：什么时候产品会接触到这条SQL能力
   - 数据同学根据你的需求写SQL取数，你需要理解SQL逻辑，判断取数范围是否正确。
   - 产品后台的列表查询功能，本质上是把页面上的筛选条件转换成WHERE条件。
   - 写PRD时描述数据规则，例如「查询2026年8月之后创建的、状态为已激活的用户」。

3. 简单示例（极简，适合阅读）：

```sql
-- 查询所有客户
SELECT customer_id, customer_name, phone
FROM customers;

-- 查询2026年注册的客户
SELECT customer_id, customer_name, register_date
FROM customers
WHERE register_date >= '2026-01-01';

-- 查询金额大于1000元的发票，按金额从大到小排，只看前10条
SELECT invoice_no, invoice_amount
FROM invoices
WHERE invoice_amount > 1000
ORDER BY invoice_amount DESC
LIMIT 10;
```

4. 【必会】PM必须掌握：
   - 能读懂SELECT、FROM、WHERE、ORDER BY、LIMIT的基本含义和顺序。
   - 理解条件过滤中的常见运算符：等于（=）、不等于（<>或!=）、大于小于（><）、区间（BETWEEN）、模糊匹配（LIKE）。
   - 知道 AND 和 OR 的区别，能用括号理解组合条件。
   - 能根据业务需求描述取数口径，例如时间范围、状态条件、字段范围。
   - 理解「去重」和「聚合」是后续更高级的需求，先有查询基础概念。

5. 【不必深入】PM不需要深入：
   - 手写复杂的多表JOIN查询和子查询。
   - 窗口函数、递归查询、存储过程。
   - SQL性能优化、执行计划分析。
   - 不同数据库方言的语法差异（MySQL、PostgreSQL、Oracle等）。

6. PM提数需求、和数据同学沟通避坑提示：
   - 明确时间口径：使用自然语言时要说明是「创建时间」还是「更新时间」，是否包含当天。
   - 说明去重规则：例如一个用户多次下单，统计用户数时要说明是否去重。
   - 区分空值处理：例如「未填写手机号」在数据库中可能是空字符串或NULL，要提前约定。
   - 字段含义确认：业务术语和数据库字段名称可能不一致，例如「订单金额」可能对应 order_amount 或 actual_pay_amount。
   - 评审SQL时多问：这个WHERE条件会不会漏掉边界数据？时间范围是否包含边界？

## 6. Python PM认知基础章节【工作台key:chapter_python】
> 面向PM：看懂Python可以解决什么问题，看懂代码逻辑，不要求独立开发项目。

### 今日知识点：Python在数据分析与自动化报表中的基础用途

1. 概念/用途通俗讲解：
   - Python是一种语法接近自然语言的编程语言，广泛应用于数据分析、自动化脚本、后端开发、人工智能等领域。
   - 对PM来说，Python的价值在于：快速处理Excel/CSV数据、自动化生成报表、原型验证数据逻辑、与数据/研发团队沟通时理解他们的工作。
   - 常用库包括 pandas（数据处理）、openpyxl（Excel读写）、requests（接口调用）、matplotlib（简单可视化）。

2. PM工作中常见使用场景：
   - 每周需要汇总多个Excel表格的数据，手动复制粘贴容易出错，可以用Python脚本自动合并。
   - 产品上线后需要统计用户行为数据，数据量不大时可以用Python快速分析并生成图表。
   - 接口测试：用Python调用产品接口，验证返回数据是否符合预期。
   - 批量处理文本：例如从大量用户反馈中提取关键词，做初步分类。

3. 【必会】PM必须掌握：
   - 知道Python能做什么、适合做什么，能在合适的场景下提出「是否可以用Python脚本自动化处理」。
   - 能看懂简单的Python代码逻辑，例如变量赋值、条件判断、循环、函数调用。
   - 理解 pandas 中 DataFrame 的基本概念：行是记录，列是字段，类似数据库表和Excel表。
   - 知道 Python 脚本通常运行在本地或服务器上，可以通过定时任务自动执行。
   - 能与研发团队沟通：把业务需求转化为「输入数据、处理逻辑、输出结果」的描述。

4. 【不必深入】PM不需要深入：
   - 独立完成大型项目开发或复杂算法实现。
   - 深入理解面向对象编程、装饰器、多线程等高级语法。
   - 搭建生产级Web服务或数据库系统。
   - 掌握机器学习模型训练和调参。

5. 和研发沟通需求时的认知提示：
   - 用业务语言描述需求，例如「每天凌晨把昨日的订单数据导出成Excel，发送到运营邮箱」。
   - 明确输入输出：输入是什么数据源？输出是什么格式？需要哪些字段？
   - 说明异常处理：如果某个字段缺失或格式错误，是希望跳过、报错还是使用默认值？
   - 区分一次性脚本和长期运行任务：一次性分析用Jupyter Notebook即可，长期任务需要考虑部署和监控。
   - 不要过度承诺：如果需求涉及大量数据或复杂逻辑，要评估是否需要专业数据工程师介入。

## 7. 今日重点总结 & PM落地提示【工作台key:chapter_summary】
> 提炼今日全部章节最核心3-4条要点，用于复盘记忆

1. 数智财税入门要聚焦业务规则和风险点：PM需要理解发票电子化流程、OCR识别后的数据流向以及识别错误的兜底方案，不需要深入研究会计做账和算法原理。
2. AI产品设计要守住能力边界：大语言模型擅长文本理解和生成，但不擅长精确计算和保证事实正确，高风险场景必须设计人工审核和RAG知识检索机制。
3. 数据库基础从表、字段、主键开始：PM要能看懂数据结构和表关系，能在PRD中清晰描述数据字段和关联逻辑，不需要会搭建和优化数据库。
4. SQL和Python是PM的「读得懂、提得准需求」的技能：能读懂简单SQL、理解取数口径，能判断Python适合处理的自动化场景，重点在于与研发和数据同学高效协作。
