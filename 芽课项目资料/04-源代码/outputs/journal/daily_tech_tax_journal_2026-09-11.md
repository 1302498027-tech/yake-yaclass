## 2. 数智财税基础章节【工作台key:chapter_tax】
> 面向PM：懂业务规则、系统流程、风险点，不做会计做账。

### 今日知识点：纳税申报流程数字化与税控设备演进

1. 核心概念：
   - 纳税申报是企业按照税法规定，定期向税务机关报送纳税申报表并缴纳税款的法定流程，常见税种包括增值税、企业所得税、个人所得税等。
   - 增值税申报频率：一般纳税人按月申报，小规模纳税人按季申报。每月/每季有固定的申报期限（通常为次月15日前，遇节假日顺延）。
   - 税控设备是过去企业开票和申报的硬件依赖，包括金税盘、税控盘、UKey等，用于发票开具、抄报税和申报。随着数电票推广，税控设备正在逐步取消。
   - 数字化申报流程：企业通过电子税务局在线填写申报表 -> 系统自动预填部分数据（如发票汇总数据） -> 企业核对并补充 -> 提交申报 -> 在线缴税 -> 获取完税凭证。

2. 业务场景举例：
   - 财税SaaS产品对接电子税务局API后，可以自动归集企业当期所有销项发票和进项发票数据，自动生成增值税申报表草稿，财务人员只需核对确认后一键提交。
   - 企业月底前在系统中查看"申报日历提醒"，系统自动展示本月需申报的税种、截止日期和准备状态，避免逾期申报。
   - 产品支持"税企直连"模式：企业ERP系统直接向税务局端推送申报数据，无需人工在税务局网站重复录入。

3. ✅ PM必须掌握：
   - 纳税申报的基本流程环节：数据归集 -> 申报表生成 -> 核对确认 -> 提交 -> 缴税 -> 完税。
   - 申报截止日期的关键性：逾期申报会产生滞纳金和信用扣分，产品必须提供申报日历和到期预警功能。
   - 税控设备正在被数电票取代的趋势，产品需要兼容"有税控设备"和"无税控设备（数电票）"两种模式的企业。
   - 申报表中数据来源的多样性：销项数据来自开票记录，进项数据来自发票勾选确认，部分数据需要手工录入（如免税收入）。
   - 自动预填功能的价值：好的财税产品能自动汇总发票数据预填申报表，减少手工录入错误和工作量。

4. ❌ PM不需要深入：
   - 增值税申报表各附表的具体填报规则和税额计算公式。
   - 税控设备的底层加密算法和数字证书签名机制。
   - 电子税务局后端的申报数据校验接口协议。
   - 企业所得税年度汇算清缴的复杂纳税调整事项。

5. 业务风险&产品设计注意点：
   - 数据准确性风险：自动预填数据如果与实际不符（如发票未全部归集），会导致申报错误，产品需提供"数据核对清单"让用户逐项确认。
   - 申报期限预警设计：产品应在截止日期前3天、前1天、当天分别推送提醒，并区分"尚未提交"和"已提交未缴税"两种状态。
   - 缴税状态同步：提交申报后缴税可能有处理延迟，产品需展示"缴税处理中"状态，避免用户重复操作。
   - 历史申报追溯：用户经常需要查看往期申报记录和完税凭证，产品需提供历史申报查询和下载功能。

## 3. AI产品基础章节【工作台key:chapter_ai】
> 面向PM：懂能力边界、适用场景、局限性，不用钻研算法原理。

### 今日知识点：Prompt工程与输出格式控制

1. 基础概念通俗解释：
   - Prompt（提示词）是用户输入给大模型的指令文本，决定了模型如何理解和回应。同一个问题，Prompt写法不同，回答质量可能天差地别。
   - Prompt工程（Prompt Engineering）是通过优化提示词的结构、内容、约束来获得更准确、更稳定输出的方法论。它不需要修改模型本身，只需要调整"怎么问"。
   - 输出格式控制是Prompt工程的核心技能之一：通过在提示词中明确指定输出格式（如JSON、表格、列表），让模型的回答可以直接被系统解析和使用，而不是输出一段自由文本。
   - 生活类比：大模型像一个很聪明但需要明确指令的助手。你说"帮我写个总结"可能得到各种风格；说"请用3个要点总结，每条不超过50字"就能得到精确可控的结果。

2. 现实产品落地案例：
   - 发票信息抽取：用户上传发票图片，系统Prompt为"请从发票中提取以下字段：发票号码、开票日期、金额、税额、销方名称，以JSON格式输出，字段名为英文"，模型输出结构化数据直接入库。
   - 智能客服回复：Prompt中规定"如果用户问题涉及退税政策，回复必须附带政策文号；如果无法确定答案，回复'请咨询专业税务师'"，确保回答安全可控。
   - 报告生成：Prompt为"请根据以下数据生成月度税务摘要，分为三个部分：收入概况、税负分析、风险提示，每部分2-3句话"，模型输出的格式统一，可以直接嵌入报告模板。

3. ✅ PM必须掌握：
   - Prompt的基本结构要素：角色设定（你是谁）、任务描述（做什么）、输出格式（怎么输出）、约束条件（什么不能做）。
   - 输出格式控制的核心方法：在Prompt中明确指定JSON/表格/列表格式，并给出示例（few-shot），让模型"照着样子"输出。
   - 理解"示例驱动"原则：给模型1-2个输入输出示例，比纯文字描述效果更好，这叫少样本提示（Few-shot）。
   - 知道Prompt的稳定性问题：同一个Prompt多次运行可能得到不同结果，产品需设计重试和校验机制。
   - 能区分"系统提示词"（产品预设、用户不可见）和"用户提示词"（用户输入），理解两者如何拼接影响最终输出。

4. ❌ PM不需要深入：
   - 大模型注意力机制如何响应不同Prompt的内部计算过程。
   - Prompt优化的学术论文级技术（如Chain-of-Thought原理、Self-Consistency机制）。
   - 模型微调和RLHF训练对Prompt响应效果的影响分析。
   - 多模态模型中图像编码与文本Prompt的对齐算法。

5. 产品需求设计、需求评审注意事项：
   - 定义输出校验规则：如果要求JSON输出，产品必须设计"格式校验 + 失败重试"逻辑，因为模型偶尔会输出非标准格式。
   - 设计Prompt版本管理：Prompt是产品的核心资产，每次修改都需要版本记录和回归测试，不能随意更改线上Prompt。
   - 安全边界设计：Prompt中必须包含"不回答什么"的约束（如不提供法律建议、不输出敏感信息），这是AI产品的合规底线。
   - 评审时多问：「如果模型输出的JSON解析失败怎么办？」「同一Prompt在不同模型版本上表现是否一致？」「用户输入恶意Prompt怎么防？」

## 4. 数据库基础章节【工作台key:chapter_db】
> 面向PM：懂数据存储逻辑、表、字段关系，不需要会搭建数据库。

### 今日知识点：索引与查询性能认知

1. 基础概念通俗解释：
   - 索引（Index）是数据库中一种特殊的数据结构，用来加速数据查询。就像书的目录：没有目录时找某个内容要逐页翻，有目录时先查目录再直接翻到对应页码，速度大幅提升。
   - 没有索引的表，查询时数据库会"全表扫描"——逐行检查每条记录是否满足条件，数据量大时非常慢。
   - 有索引的表，查询时数据库先在索引中快速定位，再直接读取对应数据行，查询速度可以从"秒级"提升到"毫秒级"。
   - 索引不是越多越好：索引会占用额外存储空间，且每次插入/更新数据时索引也需要同步维护，写多读少的表上建太多索引会拖慢写入速度。

2. 业务类比举例：
   - 发票表场景：发票表有100万条记录，如果按"发票号码"查询某张发票，没有索引时需要逐条比对100万次；在"发票号码"字段上建索引后，数据库可以快速定位，几毫秒就能找到。
   - 报销单查询场景：用户经常按"申请人姓名"和"提交日期范围"筛选报销单，如果这两个字段没有索引，当数据量增长到几十万条时，列表加载会明显变慢。
   - 反面类比：如果给发票表的每个字段都建索引，虽然查询快了，但每次批量导入1万张发票时，索引维护会导致导入耗时大幅增加。

3. ✅ PM必须掌握：
   - 理解索引的作用是加速查询，原理类比"书的目录"，能在需求评审中理解开发说的"这个字段需要加索引"。
   - 知道"高频查询条件字段"适合建索引，如发票号码、报销单号、申请日期等用户经常筛选的字段。
   - 理解索引有代价：写入和更新数据时索引需要同步维护，不能在所有字段上无限制建索引。
   - 能在需求中识别"性能风险场景"，如用户列表页需要支持多维度筛选时，主动和开发讨论哪些筛选条件需要索引。
   - 知道"索引失效"的概念：某些查询写法会导致索引不被使用（如在索引字段上使用函数或模糊查询），PM需理解这是性能问题的常见原因。

4. ❌ PM不需要深入：
   - 索引的底层数据结构（B+树、哈希索引、聚簇索引）的实现原理。
   - 查询执行计划的解读和优化（EXPLAIN分析）。
   - 数据库存储引擎级别的索引参数调优。
   - 复合索引的最左前缀原则和索引下推等高级优化策略。

5. 做需求、写PRD时相关注意点：
   - 标注高频查询场景：在PRD中说明"用户最常按哪些条件搜索/筛选"，帮助开发判断需要在哪些字段上建索引。
   - 关注大数据量场景：如果某张表预计数据量超过10万条，需在评审时主动讨论是否需要索引、查询是否会变慢。
   - 列表分页设计：数据量大时列表必须分页（如每页20条），避免一次性查询返回全部数据导致页面卡顿或接口超时。
   - 模糊搜索的权衡：LIKE '%关键词%'查询无法利用索引，如果产品需要全文搜索功能，应考虑使用搜索引擎（如Elasticsearch）而非依赖数据库LIKE查询。

## 5. SQL PM必备基础章节【工作台key:chapter_sql】
> 面向PM：看得懂简单SQL逻辑、理解取数逻辑，不要求手写复杂生产SQL。

### 今日知识点：GROUP BY与聚合函数（COUNT/SUM/AVG）

1. 概念/语法通俗讲解：
   - 聚合函数是对一组数据进行汇总计算的函数，常用的有：COUNT（计数）、SUM（求和）、AVG（平均值）、MAX（最大值）、MIN（最小值）。
   - GROUP BY是"分组"关键字，作用是按某个字段把数据分成若干组，然后对每组分别计算聚合值。
   - 生活类比：GROUP BY就像Excel的数据透视表——你选择"按部门分组"，然后对每个部门的"金额"列求和，就得到了每个部门的报销总金额。
   - 基本语法：`SELECT 分组字段, 聚合函数(数值字段) FROM 表 GROUP BY 分组字段;`
   - HAVING子句：用来过滤分组后的结果（类似WHERE，但WHERE过滤行、HAVING过滤组）。例如"只看报销总金额超过1万元的部门"。

2. 业务场景：什么时候产品会接触到这条SQL能力
   - 报表需求："统计每个部门本月的报销总金额" -> 按部门分组，对金额求和。
   - 数据看板需求："统计每种发票类型的数量占比" -> 按发票类型分组，计数。
   - 异常监控需求："找出提交报销单超过5次的员工" -> 按员工分组，计数后用HAVING筛选大于5的。

3. 简单示例（极简，适合阅读）：

```sql
-- 统计每个部门的报销总金额
SELECT department, SUM(amount) AS total_amount
FROM reimbursements
WHERE status = 'approved'
GROUP BY department;

-- 统计每位员工提交的报销单数量
SELECT applicant, COUNT(*) AS submit_count
FROM reimbursements
GROUP BY applicant;

-- 找出报销总金额超过10000元的部门
SELECT department, SUM(amount) AS total_amount
FROM reimbursements
WHERE status = 'approved'
GROUP BY department
HAVING SUM(amount) > 10000;
```

4. ✅ PM必须掌握：
   - 理解聚合函数的作用：COUNT计数、SUM求和、AVG平均、MAX/MIN极值，能在需求中正确描述需要哪种汇总。
   - 理解GROUP BY的分组逻辑：按哪个字段分组，就是对哪个维度的数据进行汇总。
   - 能看懂GROUP BY + 聚合函数的SQL逻辑，知道结果中每一行代表"一个分组的汇总值"。
   - 理解WHERE和HAVING的区别：WHERE在分组前过滤行，HAVING在分组后过滤组。
   - 知道"分组后SELECT只能选分组字段或聚合函数"这一规则，不能在SELECT中随意放未分组的字段。

5. ❌ PM不需要深入：
   - 复杂的多层嵌套子查询配合GROUP BY使用。
   - 窗口函数（如ROW_NUMBER、RANK OVER PARTITION BY）的高级用法。
   - GROUP BY的执行计划分析和性能优化。
   - 多列分组时的执行顺序和索引利用策略。

6. PM提取数需求、和数据同学沟通避坑提示：
   - 说清"按什么分组"和"算什么指标"：不要只说"统计一下报销数据"，要说清楚"按部门分组，对金额求和，只看已审批的"。
   - 注意NULL值的处理：AVG和COUNT对NULL的处理不同——COUNT(*)统计所有行，COUNT(字段)不统计该字段为NULL的行。需求中要说明空值是否算入统计。
   - 分组维度的唯一性确认：按"部门"分组时，部门名称是否唯一？如果同一部门有多个名称变体（如"财务部"和"财务部门"），结果会被拆成两组，需要先统一数据。
   - HAVING和WHERE不要混用：如果要过滤的是原始数据（如只看已审批的），用WHERE；如果要过滤的是汇总后的结果（如总金额超1万），用HAVING——搞反了会报错或结果不对。

## 6. Python PM认知基础章节【工作台key:chapter_python】
> 面向PM：看懂Python可以解决什么问题，看懂代码逻辑，不要求独立开发项目。

### 今日知识点：循环与列表操作（for/while/list）

1. 概念/用途通俗讲解：
   - 列表（list）是Python中最常用的数据容器，可以存放多个数据项，用方括号表示，如 `invoices = [100, 200, 350]` 存了三张发票的金额。
   - 列表常用操作：通过索引访问元素（`invoices[0]`取第一个）、追加元素（`append()`）、获取长度（`len()`）、遍历列表。
   - for循环用于遍历列表中的每个元素并执行操作。例如"对每张发票金额乘以税率，算出税额"。
   - while循环用于满足条件时重复执行。例如"只要还有未处理的发票就继续处理"。
   - 生活类比：for循环就像"流水线作业"——对传送带上的每个零件（列表元素）依次执行同一套动作；while循环像"排队叫号"——只要还有人排队就继续叫号。

2. PM工作中常见使用场景：
   - 数据同学展示的批量处理脚本：用for循环遍历一批发票记录，逐条校验金额和税率是否匹配。
   - 自动化报表生成：用循环遍历多个部门，为每个部门生成一份报销汇总表。
   - 数据清洗逻辑：遍历一个列表中的所有发票号，检查格式是否合规，将不合规的收集起来生成报告。

3. ✅ PM必须掌握：
   - 能看懂列表的基本结构 `[元素1, 元素2, 元素3]` 和索引从0开始（第一个元素是 `list[0]`）。
   - 能看懂for循环的遍历逻辑：`for item in items:` 表示"对items列表中的每个元素依次执行下面的代码"。
   - 理解循环中的"累加"模式：初始化一个变量为0，循环中每次加上当前值，最终得到总和——这是SUM聚合的代码实现逻辑。
   - 能理解"列表嵌套列表"的结构，如 `[[部门A, 5000], [部门B, 3000]]` 表示每项又是一个列表。
   - 能把业务需求翻译为"遍历 -> 判断 -> 处理"的逻辑描述，和研发沟通时对齐处理思路。

4. ❌ PM不需要深入：
   - 独立编写多层嵌套循环和复杂列表推导式代码。
   - Python迭代器协议和生成器函数的底层机制。
   - 列表的内存管理和深拷贝/浅拷贝区别。
   - 多线程/多进程并发编程中的循环控制。

5. 和研发沟通需求时的认知提示：
   - 用"遍历-判断-处理"框架描述批量逻辑：遍历什么数据？每条判断什么条件？满足条件后做什么处理？
   - 明确"处理边界"：循环处理一批数据时，如果某条数据异常怎么办？是跳过还是中止？是记录日志还是报错？这些边界行为需在需求中明确。
   - 确认"数据量级"：遍历100条和遍历100万条的处理策略完全不同，大数据量可能需要分批处理和进度展示，PM需在需求中说明数据量预期。
   - 注意"空列表"场景：如果列表中没有数据，循环不会执行，产品需考虑"无数据时给用户什么提示"。
