## 2. 数智财税基础章节【工作台key:chapter_tax】
> 面向PM：懂业务规则、系统流程、风险点，不做会计做账。

### 今日知识点：数电票（全面数字化电子发票）与电子税务局

1. 核心概念：
   - 数电票（全电发票）是全面数字化的电子发票，不需要纸质介质，也不依赖税控设备（如UKey、金税盘），直接通过电子税务局在线开具。
   - 传统电子发票往往还是"纸质发票的电子版"（如PDF电子发票），需要税控设备才能开具；数电票则是"从出生就是数字化的"——从开票到交付到入账到归档，全流程线上完成。
   - 电子税务局是国家税务总局提供的线上办税平台，企业可以在上面完成申报、缴税、发票管理、证明开具等操作。
   - 数电票的关键特征：没有"发票代码+发票号码"的纸质版式概念，而是以"数电票号码"作为唯一标识，并带有动态二维码用于查验。

2. 业务场景举例：
   - 企业通过电子税务局或对接开票API，销售完成后自动触发开票，购买方在手机或邮箱即时收到数电票，无需等待邮寄。
   - 买方收到数电票后，可通过电子税务局的"发票勾选确认"功能，选择哪些发票用于进项税额抵扣，替代了传统的认证报税流程。
   - 财务SaaS产品对接数电票接口后，可以自动归集企业收到的所有数电票，形成进项发票池，支持自动匹配采购订单和报销单。

3. ✅ PM必须掌握：
   - 数电票与普通电子发票的核心区别：无需税控设备、全流程线上化、以号码为唯一标识。
   - 数电票的生命周期：开票 -> 交付 -> 接收 -> 入账 -> 勾选抵扣 -> 归档。
   - 电子税务局是数电票的核心载体，PM需要理解哪些操作必须在税务局端完成（如红字发票申请），哪些可以在企业系统端完成（如归集、入账）。
   - 数电票涉及"红字发票"流程（即发票冲红/作废），规则比纸质发票更复杂，需要理解蓝字发票和红字发票的关系。
   - 产品需要支持数电票格式文件的预览和下载（如XML格式数据文件 + PDF版式文件）。

4. ❌ PM不需要深入：
   - 数电票底层的加签验签、CA证书非对称加密的技术实现。
   - 增值税进项转出、视同销售、留抵退税等复杂税务会计处理。
   - 电子税务局的系统架构和后端接口协议细节。
   - 数电票的版式文件格式标准（如OFD/PDF的底层规范）。

5. 业务风险&产品设计注意点：
   - 开票额度管理：税务机关对企业有月度授信额度限制，产品需展示可用额度并做超额预警。
   - 红字发票规则复杂：部分冲红需要购买方确认，全额冲红流程不同，产品流程设计必须区分场景，否则会导致开票方/接收方对账混乱。
   - 数据同步时效：企业系统与电子税务局之间的数据同步可能存在延迟，产品需告知用户"可能需要等待N分钟同步"。
   - 兼容性风险：过渡期内企业可能同时收到数电票和传统电子发票，产品需统一管理不同票种，避免遗漏。

## 3. AI产品基础章节【工作台key:chapter_ai】
> 面向PM：懂能力边界、适用场景、局限性，不用钻研算法原理。

### 今日知识点：RAG（检索增强生成）——让AI"查资料"再回答

1. 基础概念通俗解释：
   - RAG（Retrieval-Augmented Generation，检索增强生成）是一种让大模型"先查资料、再回答"的技术方案。
   - 纯大模型的问题：训练数据有截止时间，不了解企业内部知识，容易"一本正经地胡说"（幻觉）。
   - RAG的做法：用户提问后，系统先从企业知识库/文档库中检索相关内容，然后把检索到的原文片段和用户问题一起交给大模型，让模型"基于这些资料"生成回答。
   - 生活类比：纯大模型像"闭卷考试"——只能靠记忆答题，可能记错；RAG像"开卷考试"——先翻到相关页面，再组织语言回答，准确率大幅提升。

2. 现实产品落地案例：
   - 企业智能客服：用户问"公司差旅报销标准是什么？"，系统从制度文档中检索差旅报销条款，模型基于原文生成准确回答并标注来源。
   - 财税政策问答助手：用户问"小规模纳税人增值税起征点是多少？"，系统检索最新税收政策文件，模型给出带政策文号引用的回答。
   - 内部知识管理平台：员工上传制度文件、操作手册后，可以直接用自然语言提问，系统从文档中找到答案并返回，无需人工翻阅。

3. ✅ PM必须掌握：
   - RAG的核心三步流程：检索 -> 拼接 -> 生成，理解每一步的作用。
   - "知识库质量决定回答质量"：如果检索到的文档本身过时或错误，模型也会给出错误回答（垃圾进、垃圾出）。
   - 向量检索的基本概念：文档被切成片段后转成"向量"（一串数字），系统通过计算相似度找到最相关片段。PM需要理解"切片大小"和"检索准确率"有关。
   - 回答需带来源引用：好的RAG产品会标注答案出自哪份文档、哪个段落，方便用户核实。
   - RAG与微调的区别：RAG是"给模型临时参考资料"，微调是"改变模型本身的知识"。PM需要根据场景选择方案。

4. ❌ PM不需要深入：
   - 向量嵌入模型（Embedding Model）的训练原理和数学公式。
   - 向量数据库的底层索引算法（如HNSW、IVF）。
   - 大模型的注意力机制、Transformer架构细节。
   - RAG的高级技术（如重排序模型Reranker、多跳检索、查询改写）的具体实现。

5. 产品需求设计、需求评审注意事项：
   - 明确知识来源范围：RAG检索哪些文档？是否包含外部网页？是否需要实时联网检索？范围不清会导致答非所问。
   - 设计"无答案"兜底：当检索不到相关内容时，产品应明确告知用户"未找到相关信息"，而不是让模型自由发挥。
   - 文档预处理需求：上传的PDF/Word需要切分、清洗、去重，PM需要定义"文档管理规范"，如文件格式限制、大小限制、更新频率。
   - 评测指标：除了回答准确率，还要关注检索召回率（相关文档有没有被检索到）和引用准确率（引用的段落是否真的支持答案）。
   - 评审时多问：「用户怎么验证这个答案是对的？」「如果知识库没更新，模型会用旧数据回答吗？」

## 4. 数据库基础章节【工作台key:chapter_db】
> 面向PM：懂数据存储逻辑、表、字段关系，不需要会搭建数据库。

### 今日知识点：表关联与外键（一对多、多对多关系）

1. 基础概念通俗解释：
   - 外键（Foreign Key）是表中的一个字段，它的值引用了另一张表的主键，用来建立表与表之间的关联关系。
   - 一对多关系（最常见）：一个"父表"记录可以对应多个"子表"记录。例如一个客户可以下多个订单，但每个订单只属于一个客户。
   - 多对多关系：需要借助"中间表"（也叫关联表/桥接表）来实现。例如一个学生可以选多门课程，一门课程也可以被多个学生选——通过"选课记录表"连接学生表和课程表。
   - 一对一关系：较少见，通常用于将一个大表拆分或存储敏感信息分离。

2. 业务类比举例：
   - 报销场景（一对多）：
     - 一张报销单可以包含多张发票（一对多关系）。
     - 报销单表（reimbursements）的主键是报销单号，发票表（invoices）中有一个 reimbursement_id 字段引用报销单号——这就是外键。
   - 采购场景（多对多）：
     - 一个采购订单可以包含多种商品，一种商品也可以出现在多个采购订单中。
     - 需要一张"采购订单明细表"（order_items），包含 order_id 和 product_id 两个外键，以及数量、单价等业务字段。

3. ✅ PM必须掌握：
   - 能在一对多场景中判断哪张是"主表"（一的一方），哪张是"从表"（多的一方），外键建在从表上。
   - 理解多对多关系必须通过中间表实现，不能在两表中直接建外键。
   - 能在PRD中用自然语言描述表关联逻辑，例如"每条发票记录关联到一张报销单"。
   - 理解"级联"概念：删除一条主表记录时，从表中关联的记录怎么办？是级联删除、设为NULL、还是禁止删除？
   - 知道外键约束可以保证数据完整性——防止在发票表中写入一个不存在的报销单号。

4. ❌ PM不需要深入：
   - 外键约束的数据库底层实现机制和性能影响分析。
   - 复杂的范式分解（第三范式、BCNF等数据库设计理论）。
   - 反范式设计、物化视图等高级优化策略。
   - 分库分表场景下的跨库外键处理。

5. 做需求、写PRD时相关注意点：
   - 明确关联关系类型：在PRD的数据模型部分，标注表之间是一对多还是多对多，附简单关系说明。
   - 定义删除策略：例如"删除报销单时，关联的发票记录如何处理？"——软删除（标记为已删除）通常比物理删除更安全。
   - 考虑数据冗余与一致性：有时为了查询效率会在从表中冗余存储主表的某些字段（如报销单号旁边冗余存储申请人姓名），需要明确冗余字段何时更新。
   - 中间表设计：多对多场景的中间表通常还需要业务字段（如数量、金额、选课时间），不要遗漏。

## 5. SQL PM必备基础章节【工作台key:chapter_sql】
> 面向PM：看得懂简单SQL逻辑、理解取数逻辑，不要求手写复杂生产SQL。

### 今日知识点：JOIN多表查询入门（INNER JOIN）

1. 概念/语法通俗讲解：
   - JOIN用于把多张表的数据"拼"在一起，基于它们之间的关联字段。
   - INNER JOIN（内连接）是最常用的JOIN类型：只返回两张表中都匹配上的记录。如果一张表有记录但另一张没有对应记录，则不会出现在结果中。
   - LEFT JOIN（左连接）：返回左表全部记录，右表没有匹配的用NULL填充。适合"主表全要，从表有就取"的场景。
   - 基本语法：`SELECT a.字段, b.字段 FROM 表A a JOIN 表B b ON a.关联字段 = b.关联字段 WHERE 条件;`
   - 表别名（a、b）：给表起一个简短的名字，方便在字段前加前缀，避免两张表有同名字段时混淆。

2. 业务场景：什么时候产品会接触到这条SQL能力
   - 报表需求：查询"每个报销单及其关联的发票明细"——需要JOIN报销单表和发票表。
   - 数据核对需求：查询"有订单但没有发票的客户"——需要LEFT JOIN找出右表为空的记录。
   - 后台列表功能：展示"订单+客户名称+商品名称"——需要JOIN三张表（订单表、客户表、商品表）。

3. 简单示例（极简，适合阅读）：

```sql
-- 内连接：查询每个报销单的报销人和关联的发票金额
SELECT r.reimburse_no, r.applicant, i.invoice_amount
FROM reimbursements r
INNER JOIN invoices i ON r.reimburse_id = i.reimbursement_id
WHERE r.status = 'approved';

-- 左连接：查询所有报销单，即使有些还没有关联发票
SELECT r.reimburse_no, r.applicant, i.invoice_amount
FROM reimbursements r
LEFT JOIN invoices i ON r.reimburse_id = i.reimbursement_id
WHERE r.status = 'approved';
-- 注意：没有发票的报销单，invoice_amount 会显示为 NULL

-- 三表连接：查询订单、客户名称和商品名称
SELECT o.order_no, c.customer_name, p.product_name
FROM orders o
INNER JOIN customers c ON o.customer_id = c.customer_id
INNER JOIN order_items oi ON o.order_id = oi.order_id
INNER JOIN products p ON oi.product_id = p.product_id;
```

4. ✅ PM必须掌握：
   - 能区分INNER JOIN和LEFT JOIN的差别：INNER只返回两边都有的，LEFT保留左表全部。
   - 理解ON后面的关联条件就是外键关系，和数据库设计中的表关系一一对应。
   - 能看懂JOINSQL的大致逻辑，知道结果中每一行是怎么"拼"出来的。
   - 理解多表JOIN时"一对多"关系会导致结果行数膨胀（一个报销单有3张发票，结果就变成3行）。
   - 能描述取数需求时说清楚"需要哪些表、通过什么字段关联"。

5. ❌ PM不需要深入：
   - 手写三层以上的复杂多表JOIN和子查询嵌套。
   - FULL JOIN、CROSS JOIN、自连接等较少用的JOIN类型。
   - JOIN的执行计划和性能优化（Hash Join、Nested Loop等）。
   - 复杂的窗口函数配合JOIN使用。

6. PM提取数需求、和数据同学沟通避坑提示：
   - 说清用INNER还是LEFT：如果需求是"列出所有报销单（含未关联发票的）"，必须说LEFT JOIN，否则INNER JOIN会丢掉没有发票的报销单。
   - 注意一对多的行数膨胀：JOIN后行数变多，如果不做聚合，统计"报销单数量"会变成统计"报销单+发票明细行数量"，结果不对。
   - 字段前缀要写清楚：多表JOIN时同名字段（如两张表都有id），SQL中必须加表别名前缀，否则会报歧义错误。
   - 验证关联键的唯一性：ON后面的关联字段在主表中是否唯一？如果不唯一，会产生笛卡尔积（行数爆炸），需要特别确认。

## 6. Python PM认知基础章节【工作台key:chapter_python】
> 面向PM：看懂Python可以解决什么问题，看懂代码逻辑，不要求独立开发项目。

### 今日知识点：变量、数据类型与条件判断（if/else）

1. 概念/用途通俗讲解：
   - 变量是给数据起的名字，用来存储和引用数据。例如 `invoice_amount = 1000` 就是把1000存到一个叫 invoice_amount 的变量里。
   - 数据类型是数据的"种类"，Python中常用的有：整数（int）、浮点数/小数（float）、字符串/文本（str）、布尔值/真假（bool）、列表（list）、字典（dict）。
   - 条件判断（if/else）是让程序根据不同情况执行不同逻辑。例如"如果发票金额大于1000，标记为'大额发票'，否则标记为'普通发票'"。
   - 条件判断是PM理解代码逻辑的入门钥匙：很多业务规则在代码中就是一连串的if/else。

2. PM工作中常见使用场景：
   - 数据同学给你看一段Python代码，你需要理解它的处理逻辑是否正确（如"这段代码是怎么给发票分类的？"）。
   - 产品需求中的业务规则，往往可以用if/else描述清楚，例如"如果用户是VIP，打8折；如果是普通会员，打9折；否则原价"。
   - 数据清洗规则经常用条件判断实现，例如"如果税率为空，默认设为0.13；如果金额为负数，标记异常"。

3. ✅ PM必须掌握：
   - 能看懂变量赋值（`变量名 = 值`）和基本数据类型的含义。
   - 能看懂if/elif/else的条件分支逻辑，理解程序的执行路径。
   - 能理解比较运算符（==、!=、>、<、>=、<=）和逻辑运算符（and、or、not）。
   - 能把业务规则翻译成"如果…就…，否则就…"的条件判断描述，和研发沟通时对齐逻辑。
   - 理解代码中的缩进（Indent）代表代码层级——Python用缩进而不是大括号来组织代码块。

4. ❌ PM不需要深入：
   - 独立编写复杂的多层嵌套条件逻辑和循环组合代码。
   - 理解Python的高级特性（列表推导式、lambda函数、生成器、装饰器）。
   - 异常处理（try/except）的完整用法和自定义异常类。
   - 面向对象编程（类、继承、多态）的设计模式。

5. 和研发沟通需求时的认知提示：
   - 用"输入-处理-输出"框架描述需求：输入是什么数据？经过什么条件判断和处理？输出什么结果？
   - 把业务规则写成决策表或流程图再交给研发，比口头描述更可靠。例如把税率规则做成一张表：收入区间 -> 适用税率。
   - 注意边界条件：if条件是"大于"还是"大于等于"？比如"金额>=1000"和"金额>1000"，边界值1000的处理完全不同。
   - 多分支场景要覆盖所有可能：if/elif/else要考虑"都不满足"的情况（else兜底），否则数据可能被遗漏处理。

## 7. 今日重点总结 & PM落地提示【工作台key:chapter_summary】
> 提炼今日全部章节最核心3-4条要点，用于复盘记忆

1. 数电票是数智财税的核心载体：PM需理解数电票"无需税控设备、全流程线上"的核心特征，掌握开票-交付-入账-抵扣-归档的生命周期，特别是红字发票流程的复杂性，但不需要深入底层加密技术。
2. RAG让AI从"闭卷考试"变"开卷考试"：PM需掌握"检索-拼接-生成"三步流程，理解知识库质量决定回答质量，产品设计必须支持来源引用和"无答案"兜底，这是企业AI问答产品的关键设计原则。
3. 表关联是数据库设计的骨架：PM要能判断一对多和多对多关系，理解外键建立关联、中间表解决多对多，在PRD中清晰描述关联逻辑和删除策略，这是写好数据相关需求的基础。
4. JOIN和if/else是PM"读懂逻辑"的两把钥匙：INNER JOIN和LEFT JOIN的区别决定取数结果是否遗漏数据；条件判断是业务规则在代码中的直接映射——掌握这两个概念，PM就能看懂大部分取数和处理逻辑。
