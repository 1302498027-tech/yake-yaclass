## 二、与 PRD 的 8 处差异

| # | PRD 原文 | 问题 | 本稿处理 |
|---|---|---|---|
| 1 | FR-07「全部内容逻辑删除，回收站 30 天」 | `t_doc/t_card/t_node/t_task` 都没有删除标记 | 四表补 `is_deleted` + `deleted_at` |
| 2 | FR-03-3「编辑采用覆盖方式并记录最后更新时间」 | `t_thought` 只有 `submitted_at` | 补 `updated_at`（`ON UPDATE`） |
| 3 | FR-03-4「每 30 秒自动保存草稿」 | 只定义了 `t_answer.content` / `updated_at` | 补 `draft_content` / `draft_saved_at` / `saved_at` / `created_at`，一人一题一行 |
| 4 | 6.3「橙色 = 打开过绑定的任一格」 | 8 个实体里没有任何"打开记录"，埋点事件不能当状态源 | 新增 `t_card_view`，支撑橙色态与"解绑后无记录"的回退判定 |
| 5 | FR-07「审计日志保留 180 天，含前后状态」 | 只有要求，没有表 | 新增 `t_audit_log`，`before/after` 用 JSON |
| 6 | FR-06「数据量大时异步导出」 | 生成完只在页面提示，用户关页就丢了 | 新增 `t_export_job`（状态 + 产物路径 + 过期时间） |
| 7 | `t_user.role` 含 `tourist` | 游客定义是「未登录」，不会产生 user 行 | 枚举收为 learner/ops/admin，游客由网关层判空 |
| 8 | FR-04「搜索响应 ≤ 1 秒」 | 正文是 `LONGTEXT`，`LIKE '%词%'` 撑不住 | 四张内容表加 `FULLTEXT ... WITH PARSER ngram` |

另外两处细节：

- **绑定表用物理删除**。绑定是"关系"不是"内容"，逻辑删除会和唯一键 `(node_id, doc_id)` 打架（解绑后重绑会撞）。解绑动作记进审计日志，同样满足 FR-07 的追溯要求。
- **`t_thought` 不存 `node_id`**。归属由 `t_node_card` 派生，这是 PRD 6.2.1「一格绑 N 个节点，思考同步归集但只计 1 条」能成立的前提；一旦把归属写死在思考行上，N 对多就会退化成复制。

## 三、ER 速览

```
t_user ──1:n── t_thought ──n:1── t_card ──n:n(t_node_card)── t_node
   │                              │                            │
   │                              └──n:n(t_node_doc)──── t_doc │
   ├──1:n── t_read_mark ─────────────────n:1─────────────────┘ │
   ├──1:n── t_card_view ────────n:1── t_card                   │
   ├──1:n── t_answer ──n:1── t_task ──n:n(t_node_task)─────────┘
   └──1:n── t_export_job

t_node.parent_id → t_node.node_id（无限层级）
```

思考的节点归属永远是「一格 → 绑定表 → 节点」两步跳，所以补绑、解绑、删节点都只需要改绑定，用户数据一条不动。

## 四、还需要产品拍板的三件事

1. **橙色态要不要给"取消打开记录"的入口。** 结构上我按"只增不删"设计了（`t_card_view` 没有删除路径），但 6.3 写的回退条件是"节点下一格全部解绑**且无打开记录**"——后半句目前只能靠解绑触发。若要坚持，需要一个用户不可见的清理策略（比如按 `last_viewed_at` 过期），否则这一条无法真正执行。
2. **`t_answer` 一人一题唯一键是否符合预期。** FR-03-4 说"保存后归档在本节点内，支持再次编辑"，我按覆盖式（一题一条）设计。如果后续要留版本历史，得改成 `(user_id, task_id, version)` 并另建当前版本指针。
3. **删除文档时要不要连带清 `t_read_mark`。** FR-07 写"清除该文档已读标记"，但已读是文档级全局状态，清了意味着用户在别处的阅读记录也消失。我按"保留"设计（文档逻辑删除，已读行不动，统计时过滤），更保守。这条需要确认。

## 五、DBA 上线检查单

- [ ] 库默认字符集 `utf8mb4`、排序 `utf8mb4_0900_ai_ci`；`character_set_server` 与连接串一致，否则中文全文索引会失效
- [ ] `ngram_token_size` 默认 2。若产品要求单字可搜，改为 1 会显著膨胀索引（约 3–5 倍），需先评估
- [ ] 时区统一：全表用 `DATETIME`，应用层统一按 UTC+8 写入，避免 `TIMESTAMP` 随 `time_zone` 漂移
- [ ] `t_thought.content` 是 `VARCHAR(200)`，**按字符计**，200 汉字没问题；但接口层要做 5–200 的双向校验，别只靠前端
- [ ] 全文索引建完后跑一次 `OPTIMIZE TABLE`，否则首次 MATCH 会走全表
- [ ] 上线前用 `yake_selftest.sql` 跑一遍，11 条必须全 PASS
- [ ] 定时任务：`t_audit_log` 180 天归档、回收站 30 天物理删除、`t_export_job` 产物 7 天过期

## 六、性能上要盯的两个点

1. **`v_user_node_state` 是 CROSS JOIN 用户 × 节点。** 视图是 `ALGORITHM=MERGE`，只要查询带上 `WHERE user_id = ?`，优化器会先把 `t_user` 过滤成一行，代价可控。**千万别不带 `user_id` 全表查**——那会退化成 用户数 × 节点数 的相关子查询。
2. **搜索走 `MATCH ... AGAINST`，不要混用 `LIKE`。** 混用会让优化器放弃全文索引。单字搜索回退 `LIKE` 时务必带上时间或节点范围，并限制条数。
